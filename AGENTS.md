# DictationApp

macOS menu-bar dictation app. Swift package: `Sources/DictationKit` (all app code), `Sources/DictationApp` (entry point), `Tests/DictationKitTests`.

`Sources/DictationKit` is one folder per feature: `App` (launch, main window, `AppServices`, where files live), `Dictation` (the controller, hotkeys, typing the text), `Audio` (mics, recording, kept recordings), `Speech` (the engines: cloud, Apple, on-device), `Polish` (AI polish, setups), `Pill` (the recording bar), `History` (History, Insights, analytics, Corrections), `Learn` (learning a prompt), `Commands` (command mode), `Settings`, `Debug` (latency probe, diagnostics). A new feature gets its own folder, with its Settings section and History view next to its logic.

## Workflow
- Before implementing a feature or fix, look for refactoring that makes it cleaner and easier to maintain (split out a testable piece, delete a workaround the change makes unnecessary) and do it as part of the change. If a change to app *behavior* would be simpler to maintain long term, don't just make it — propose it to the user with the trade-off and let them decide.
- Shared objects (settings, History, Insights, recordings, commands, Learn) are made once in `AppServices.live()` and handed in; no `static let shared` and no `= .shared` defaults (`ArchitectureTests` checks). Tests build theirs with `makeServices(self)`, which uses temporary files, so they never touch the user's data.
- Before building or committing: `./test.sh` (unit, UI, snapshot and perf-budget tests). Every new feature or fix gets tests in the same change:
  - logic → unit tests with injected `UserDefaults` / file URLs / pasteboards (see `TestSupport.swift`), never the user's real ones;
  - UI → `HostedView` + accessibility identifiers (`.accessibilityIdentifier`), driven with `click(_:)`; add a snapshot for new visual surfaces;
  - tests fail only on bugs, never on this Mac's setup: snapshots come from a fixed-scale window (`HostedView`, `OffscreenPanel`; `assertSnapshot` refuses others), and views take dates from `\.dateContext` rather than `Date.formatted()`, so display, region, clock, time zone and accent color don't change them;
  - hot paths (audio thread, overlay, history I/O) → an `assertFaster` budget in `PerformanceTests.swift`.
- On-device speech changes (`LocalSpeech.swift`, the MLX packages): also run `./test.sh --local` (the real Qwen model through `LocalEngine`, and a real first download into an empty cache), then `bench/suite.py latency run --alongside --local -P none`. Building needs Xcode's Metal Toolchain (MLX's GPU code): `~/github/homelab` → `ansible-playbook mac.yml -t xcode -K`.
- Command mode (`Commands/`): `./test.sh --live` also asks the real Jev (decisions API) through `CommandMode.handle`. Example commands ship in the app and are copied into `~/Library/Application Support/DictationApp/Commands` once (first launch); after that the folder is the user's, so change an example there too if they should get it.
- Cloud calls go through `OpenRouter` (`App/OpenRouter.swift`: `chat`/`post`, `send`, `content`, the reasoning-off rule); the bench's equivalent is `bench/openrouter.py` (key from `$OPENROUTER_API_KEY` or the app's saved one).
- Cloud transcription changes: also run `./test.sh --live` (real API, both cloud models). Live and integration tests must exercise the app's real code path (e.g. `CloudEngine.stop()`), not a test-only helper — a helper hid the unfinished-WAV bug that only the real path had.
- Intentional UI change: `RECORD_SNAPSHOTS=1 ./test.sh --filter SnapshotTests`, then look at the new PNGs in `Tests/DictationKitTests/__Snapshots__/` before committing. If it shows in the README's animations (the pill, Settings › Speech model, History, Corrections, analytics), rebuild them: `scripts/readme-gifs.py render` (scenes: `ReadmeFrames.swift` + snapshots).
- Dictation turnaround (stop → text, per speech/polish model): `bench/suite.py latency run` (drives the installed app; see `bench/README.md`). Run it after changes to `CloudEngine`, `SpeechEngine.stop` or polish.
- AI polish model or prompt changes: `bench/suite.py polish run` (quality on tricky dictations + wait; see `bench/results/polish/README.md`). Setups (speech + polish model + prompt) are in `Sources/DictationKit/Polish/Setups.swift`; keep each `PolishPrompt` version identical to `bench/polish_prompts/<version>.txt` (a bench test checks), and add a new version rather than editing one a setup uses.
- App-level perf (launch time, idle CPU, memory): `scripts/perf.sh` (also `./test.sh --perf`). Run it after changes to launch, audio or anything that runs in the background.
- Minor changes (copy/text tweaks, small fixes): commit and push, but don't rebuild or relaunch — it interrupts the user. They'll ship with the next major build.
- After every major feature change: run `./build.sh --keep-running`. It compiles and installs to `/Applications/DictationApp.app` without quitting the running copy, so a dictation in progress is never cut off; the running app relaunches into the new build as soon as it is idle (a copy left running on replaced files gets only silence from the mic). Do it once the change compiles; don't ask first. Plain `./build.sh` (quits and relaunches) only when the user asks for a restart.
- Builds are signed with a stable self-signed cert ("DictationApp Local Signing", in `~/Library/Keychains/dictationapp-signing.keychain-db`, created by `build.sh` on first run), so permissions survive rebuilds. Don't switch back to ad-hoc signing (`--sign -`): it changes the signature each build and silently voids the Accessibility grant.
- The cloud API key lives in `~/Library/Application Support/DictationApp/secrets.json` (0600, folder 0700; `FileSecretStore`), not the Keychain: with no Apple team ID the Keychain treats every build as a new app and asks for the login password again. Don't move it back unless builds get a Developer ID.
